# 阿德小厨房 · Docker 自托管版

给家庭主厨使用的私人点菜网页。朋友可以在手机上选菜、提交饭局信息；主厨工作台负责接单、管理菜谱、生成采购清单和记录家宴。

本项目现在以 **腾讯云轻量应用服务器上的 Docker 自托管**为主要运行方式，同时保留极空间 NAS 的兼容部署：

- 菜谱、订单、库存、邀请保存在宿主机挂载目录中的 SQLite 数据库。
- 菜品照片和家宴照片保存在宿主机挂载目录，不写入容器临时层。
- 主厨工作台使用独立密码与安全会话保护。
- Docker 容器提供健康检查，备份容器每天备份数据库并镜像照片目录。
- GitHub 每次收到 `main` 分支更新后会先自动测试，再发布新的 `linux/amd64` Docker 镜像。
- 智能菜谱录入使用通义千问 Qwen3-VL-Plus 读取截图、书页照片、食材和步骤；不配置时仍支持文字菜谱解析。
- 主厨工作台按“接单 → 订单和采购 → 制作 → 开饭”展开；接单页汇总朋友订单并可直接编排宴席菜单。通知开饭与归档分成两个动作，主厨在饭局真正结束后手动确认归档。
- 朋友下单后，当前浏览器会记住尚未归档的饭局；再次打开普通菜单或邀请链接时会自动回到进度页。只有主厨确认归档后，朋友再次进入才会看到新的点菜页面。
- 专属邀请可选择“多人共享一张单”：同一链接可发给一桌朋友，每个人用自己的称呼加入并实时同步选菜，服务器汇总后生成一份兼容现有订单、进度提醒和正式菜单推送的饭局；另一场饭局使用另一条链接，数据完全隔离。
- 制作执行台会同步日期、人数、忌口、按菜谱原始分量列出的用料和完整步骤；订单人数与点菜数量都不会改变单道菜的原始用量，并提供合并备菜、按开饭时间倒排、单菜计时器与库存不足提醒。
- 宴席编排器提供 10 套独立主题：温馨家宴、二人世界、Fine Dining、新春团圆、中秋雅宴、生日烛光、乔迁暖居、夏日晚风、冬日圣诞和周末早午餐；每套背景都只装饰页边，保证菜单正文易读。
- 通义千问会为识别出的菜谱生成 22–42 字、凝练有画面的菜品介绍，以及通常 10–24 字、以菜品知识作底并带口语吐槽反转的“阿德式”点菜 slogan；两项都能在菜单编辑中修改或单独重新生成，完整风格基准见 `COPY_STYLE.md`。
- 主厨端支持批量导入结构化 JSON 菜谱：先预览新增与更新数量，确认时自动备份数据库并按菜名合并，原有菜品照片和菜单状态不会被覆盖。
- 菜谱截图、菜品封面、制作过程图和餐桌日记照片在电脑端都可直接拖入对应上传区；点击选择和手机相册上传方式继续保留。
- 菜品封面上传后会在浏览器本地智能寻找主体，并支持拖动、焦点滑杆和 60%–220% 缩放微调；缩小时使用原图柔化背景自然补边，保存时会按预览画面真实生成统一比例封面并存入宿主机数据目录。粘贴网络图片地址后会实时通过同源安全代理预览，确认取景后转存本地，不依赖外站长期可用。
- 朋友点菜首页保留温暖红色卡片布局，以竖版主厨肖像制作杂志封面式首屏，并在菜品区后使用横版厨房肖像作为主厨见面礼。
- 手机点菜区使用左侧固定大类、右侧连续菜品列表；“阿德推荐”以独立横向卡片置顶，电脑端也有独立的主厨推荐区。点击分类会定位到第一道菜，右侧滚动时左侧分类会自动同步高亮；手机与电脑均可点击菜品照片打开全屏大图，不影响加菜操作。
- 菜品大类支持在主厨端填写自定义 Emoji、改名、任意排序和删除；新建大类同样可以移动到最前，删除大类后原有顺序保持稳定，其中菜品只会移入“未分类”，不会被删除。
- 完整菜谱库使用可连续滚动的瀑布流，并支持多选菜品后批量加入指定大类；分类筛选和批量操作的目标大类下拉会实时跟随“菜品类型管理”的顺序。新建菜品优先选择已有类型，只有选择“自定义新类型”后才可录入新类型。
- 已归档菜品仍可在菜谱库直接编辑、恢复或永久删除。
- 菜谱库可按单个大类进入排序模式，把菜品上移、下移、置顶或置底；朋友点菜端会同步这个顺序，归档菜品自动排在末尾。
- 家宴编排器会按“前菜 → 热菜 → 主食 → 汤饮甜品”自动分组；菜品换栏目后立即归位，上下移动只调整同一栏目内的出菜顺序。正式菜单可直接导出 PNG、JPG 或 PDF，图片格式适合发微信，PDF 适合归档。
- 家宴正式菜单可选择对应订单推送到朋友的实时进度页；朋友会收到新菜单弹窗并可随时查看完整主题菜单，主厨再次推送后页面自动更新。
- 朋友确认状态提醒或打开正式菜单后会回传已读回执，主厨端可以看到朋友是否已经确认提醒或查看菜单；网络短暂失败时会自动重试回执。
- 宴席编排器只列出进行中的饭局；饭局完成或取消归档后不能再推送菜单，朋友下次打开旧进度链接时会回到新的点菜首页。
- 主厨端可切换“厨房今日营业 / 厨房今天休息”；状态保存在宿主机 SQLite，朋友端同步显示绿灯或红灯。休息时仍可浏览完整菜单，但普通菜单和专属邀请都不能加菜、结算或提交订单。
- 餐桌日记拥有独立主厨入口：普通点菜和专属邀请只要进入开饭状态都可以选填一篇，支持照片、反复编辑和删除；删除日记不会删除原饭局，之后仍可重新补写。
- 微信链接卡片使用独立的 800×800 正方形轻量分享图，并按 `PUBLIC_ORIGIN` 或代理转发协议输出绝对地址；云服务器直接使用 HTTP 时不会错误生成 HTTPS，接入 HTTPS 反向代理后也能保持安全地址。
- 正式图标采用“筷子夹红烧肉、盘面投影德字”的暖红插画，浏览器、iPhone、PWA 与微信分享卡片保持统一；朋友端每次进度强提醒会按不同阶段显示对应 Emoji。

## 腾讯云轻量应用服务器部署

当前生产环境使用 Ubuntu + Docker，容器内部固定监听 `3000`，宿主机把 `/data` 挂载到容器 `/data`，把 `/backups` 挂载到容器 `/backups`。云服务器请使用 `compose.cloud.yaml` 和 `cloud.env.example`，不要直接套用 NAS 的 3099 端口配置。

镜像的依赖阶段会固定使用 Node.js 22.13.0，并预装 Python、`make` 和 `g++`，用于编译 `better-sqlite3` 等原生依赖。不要在容器外先执行 `pnpm install` 后再复制 `node_modules`；如果使用云平台的源码构建模式而不是本仓库 Dockerfile，请将构建运行时设为 Node.js 22.13 或以上，并安装 Python 3、`make` 和 `g++`。

```bash
cp cloud.env.example .env
# 编辑 .env，至少填写 CHEF_PASSWORD 和 AI 接口 Key；若直接用公网 HTTP:3000，填写 PUBLIC_ORIGIN=http://公网IP:3000
docker compose -f compose.cloud.yaml up -d --build
```

云端默认 `PUID=0`、`PGID=0`，用于避免 `/data` 挂载目录和 Next 缓存的权限冲突。长期公开分享建议在应用前配置 HTTPS 反向代理；此时把 `PUBLIC_ORIGIN` 填成最终的 `https://` 域名。更新代码后执行 `docker compose -f compose.cloud.yaml up -d --build`，数据不会因重建容器而删除。

## 极空间 Z4Pro 部署

### 1. 准备目录

在极空间硬盘中建立两个文件夹，例如：

- `Docker/阿德小厨房/data`
- `Docker/阿德小厨房/backups`

`data` 是正式数据，`backups` 是每日备份。建议放在具备冗余保护的存储池，并把备份目录额外同步到另一块硬盘或网盘。

### 2. 准备环境配置

把 `nas.env.example` 复制为 `.env`，至少修改：

```dotenv
CHEF_PASSWORD=一段至少10位且只有你知道的密码
NAS_DATA_PATH=/极空间中实际选择的数据目录
NAS_BACKUP_PATH=/极空间中实际选择的备份目录
```

如果极空间的 Compose 页面提供文件夹选择器，以选择器生成的宿主机路径为准。不要把 `.env` 提交到 GitHub。

智能菜谱图片识别需要额外填写：

```dotenv
OPENAI_BASE_URL=https://dashscope.aliyuncs.com/compatible-mode/v1
OPENAI_API_KEY=你的阿里云 DashScope API Key
OPENAI_MODEL=qwen3-vl-plus
```

API Key 只保存在实际运行服务器的环境变量中。上传的菜谱截图会发往通义千问进行当次识别，识别完成后只把你确认保存的结构化菜谱写入本地数据目录；截图本身不会作为菜品照片自动保存。菜单编辑中的“千问再生成”同样使用这套配置，只把当前菜名、配方、步骤和已有文案发给千问。

### 3. 首次连接 GitHub 镜像仓库

正式镜像位于：

```text
ghcr.io/adechokwok/ade-private-kitchen:latest
```

仓库和 GHCR Package 都设为公开后，极空间可以直接拉取镜像，不需要 GitHub 用户名或 Token。仓库公开不会自动保证旧 Package 同步公开；如果仍提示无权限，请在 GitHub Package settings 中把镜像可见性改为 Public。

### 4. 创建 Compose 项目

在极空间 Docker 中创建 Compose 项目，使用本项目的 `compose.nas.yaml`，并加载第 2 步准备好的 `.env`。它会直接拉取已在 GitHub 测试通过的 `linux/amd64` 镜像，然后启动：

- `ade-private-kitchen`：点菜网页与主厨工作台
- `ade-private-kitchen-backup`：每日自动备份

默认端口为 `3099`。局域网访问地址通常是：

```text
http://NAS局域网IP:3099
```

确认 `/api/health` 返回 `ok: true` 后，再在极空间“远程访问”中添加这个网页服务。

远程访问必须使用公网 HTTPS，并允许微信抓取页面与 `/wechat-share.jpg`。新分享图上线后，微信可能仍缓存旧卡片；首次验证时可在链接末尾临时加一个无害查询参数（例如 `?share=2`）触发重新抓取。

### 5. 首次登录

朋友点菜页：`/`

主厨工作台：`/chef`

主厨登录密码就是 `.env` 中的 `CHEF_PASSWORD`。连续输错会触发临时限制；登录会话默认保留 7 天。

## 数据位置

容器内部的数据结构：

```text
/data/
├── ade-kitchen.sqlite       # 菜谱、订单、库存与邀请
├── ade-kitchen.sqlite-wal   # SQLite 运行文件
├── .session-secret          # 自动生成的会话密钥
├── uploads/                 # 菜品图、过程图与家宴照片
└── import-backups/          # 每次批量导入前自动创建的数据库备份

/backups/
├── ade-kitchen-*.sqlite     # 按日期保存的数据库备份
└── uploads-latest/          # 最新照片镜像
```

数据库备份默认保留 14 天，可以通过 `BACKUP_RETENTION_DAYS` 修改。备份间隔默认 24 小时。

### 批量导入菜谱

登录主厨工作台，进入“菜单管理 → 批量导入菜谱库”，选择包含 `recipes` 列表的 UTF-8 JSON 文件。系统会先显示菜谱总数、将新增和将更新的数量；点击确认后才会执行导入。

同名菜只更新分类、介绍、口号、用量和做法，原有照片、上下架、推荐和售罄状态会保留。新菜默认加入菜单。正式写入前数据库会自动备份到 `/data/import-backups/`，任何一道菜写入失败都会回滚整批导入。

### 全量数据迁移

登录 `/chef` 后，在“数据迁移”工具中可以“导出全部数据”或“导入备份”。导出 ZIP 包含 `export.json`、SQLite 业务数据以及 `/data/uploads/` 下的全部照片和元数据；导入会先创建当前数据库备份，再在事务中整体替换业务表并替换图片。非敏感 `app_settings` 会按备份完整对齐（包括删除目标端多余项），密码、会话密钥和 API Key 等运行时敏感配置不会被导入覆盖。导入压缩包仅接受 `export.json` 与 `uploads/` 路径，并会拒绝目录穿越。

## 后续更新流程

以后每次迭代按这条固定链路进行：

```text
修改并测试 → 推送 GitHub main → GitHub 自动构建镜像 → 极空间确认更新
```

GitHub 中的“测试并发布 NAS 镜像”显示绿色后，在极空间打开这个 Compose 项目，执行“拉取最新镜像”并重新创建或重新部署容器。若使用命令行，对应操作是：

```bash
docker compose -f compose.nas.yaml pull
docker compose -f compose.nas.yaml up -d
```

`latest` 代表最新稳定版本，同时每次发布还会保留一个 `sha-完整提交编号` 标签，出现问题时可以把 `compose.nas.yaml` 里的镜像标签临时改成上一个编号并重新部署。

数据目录使用独立挂载，更新或重新创建容器不会删除菜谱和照片。更新前仍建议确认备份容器最近一次执行成功。当前保留人工确认更新，避免尚未查看的新版本在饭局进行中自动重启服务。

### 更新状态在哪里看

- GitHub 仓库的 **Actions** 页面：查看自动测试与镜像发布是否成功。
- GitHub 仓库的 **Packages** 区域：查看 `latest` 和各个历史版本镜像。
- 极空间 Docker 项目：拉取新镜像后重新部署，并确认两个容器恢复为健康状态。

## 本机开发

需要 Node.js 22.13 或以上和 pnpm 11。

```bash
cp .env.example .env.local
pnpm install
pnpm dev
```

常用命令：

- `pnpm build`：构建生产版本
- `pnpm test`：构建并运行自动检查
- `pnpm nas:backup`：执行一次本地备份
- `docker compose up -d --build`：从当前源码构建开发版
- `docker compose -f compose.nas.yaml up -d`：使用 GitHub 镜像启动极空间正式版

## Mac 与 Windows 双端继续开发

仓库根目录的 `AGENTS.md` 是项目的跨设备长期记忆，记录产品目标、Docker 本地磁盘架构、发布流程与安全边界。新电脑或新对话开始开发前，应先同步 GitHub 最新版本，并让 Codex 完整阅读 `AGENTS.md` 和本文档。

两端共享代码和项目记忆，但不共享 `.env`、密码、Token 或 API Key；这些配置应分别安全保存在对应电脑或 NAS 上。不要用压缩包来回覆盖项目，统一通过同一个 GitHub 仓库同步，避免丢失另一端的修改。

## 从旧云端版本迁移

旧版使用 Cloudflare D1 和 R2，不能直接复制数据库文件到云服务器或 NAS。正式切换前，需要从旧版导出菜谱、订单与照片，再导入当前 Docker 版本。迁移完成并核对数据后，再停止旧站点，避免两边产生不同订单。
